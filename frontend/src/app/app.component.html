Bienvenue ! À quoi sert ce kiosque, et par où commencer ?

Ce kiosque est un atelier interactif : en cinq étapes (environ {{ totalMinutes }} minutes), vous découvrez comment des logiciels se parlent grâce à une API, et comment une IA peut aider à les construire. Aucun prérequis : vous lisez, vous cliquez, vous essayez avec une vraie API.

  • Un mot vous échappe ? Le bouton (en haut de la page) l’explique avec des mots simples.
  • Les étapes 2 à 5 commencent par « En deux mots » : l’essentiel, une comparaison avec la vie courante et ce que vous allez faire.
  • Les passages « Côté technique » sont repliés : ouvrez-les si le détail vous intéresse, passez-les sinon.
  • Les « missions » sont de petites actions à réaliser (ouvrir, copier, appeler une API…). La barre sous les onglets les compte : rien n’est noté, elle sert à vous repérer.

Essayer ici, sans enregistrer de fichier

Le code de l’IA est prêt ? Collez-le dans une fenêtre d’essai isolée du kiosque : la page s’affiche comme dans un navigateur, et un journal montre les appels qu’elle envoie à l’API.

Attention à la clé. Une page HTML qui appelle l’API directement doit connaître la clé : toute personne qui ouvre la page, ou qui presse F12, peut la lire. C’est acceptable pour un essai sur votre poste, jamais pour une page publiée. C’est la raison d’être du petit serveur (le BFF) de ce kiosque : la clé reste côté serveur.

Quota. La formule gratuite de TheCatAPI est limitée à 10 requêtes par minute : si plusieurs personnes testent en même temps avec la même clé, certaines recevront un 429 (« trop de demandes »). Patientez une minute : c’est un cas d’école de statut d’erreur.

À retenir. Une fois curl validé, l’IA peut accélérer la production d’une page web. Le contrat reste la référence, et la clé reste un secret.

Un repère de maturité : les niveaux de Richardson

Quatre niveaux pour une API web : nous visons le niveau 2

Le « modèle de Richardson » (du nom de son auteur) classe les API web en quatre niveaux, du plus rudimentaire au plus abouti. Pour chacun, imaginez un guichet :

    @for (level of richardson; track level.level) {

  1. Niveau {{ level.level }}@if (level.chosen) { Notre choix }

    {{ level.name }}

    {{ level.idea }}

Pourquoi le niveau 2 ? Il suffit à rendre l’API compréhensible par une personne, un outil ou une IA : chaque ressource a son adresse, chaque méthode son sens, chaque statut son résultat. Le niveau 3 demande plus de conception, pour un bénéfice que peu d’applications exploitent.

Côté technique Ce que nous constatons… et ce que nous ne prétendons pas

Dans les réponses vues ici, nous ne trouvons pas de liens vers des actions possibles : nous ne constatons donc pas de niveau 3, sans prétendre avoir audité toute l’API. Les exemples des niveaux 0 et 3 sont fictifs, ceux des niveaux 1 et 2 sont de vrais appels.

Vous l’avez déjà pratiqué à l’étape 1 : GET /breeds/abys sans clé donne un 403, GET /breeds/char avec la clé donne un 200. Dans la fenêtre « Jouer », saisissez un identifiant inconnu comme zzz pour obtenir un 404.

Ressource = l’adresse Le chemin désigne la chose demandée : /breeds (les races), /breeds/{id} (une race), /images/search (des photos).

Méthode = le verbe GET lit. POST écrit, par exemple pour créer un favori.

Statut = le résultat 200 ça a marché · 403 accès refusé · 404 introuvable · 429 trop de demandes.

Comment lire cet échange ?

Chemin : l’adresse de la chose demandée (la ressource). Paramètres : ce qui suit le « ? », par exemple q=siam pour chercher « siam ». JSON : le format texte dans lequel l’API renvoie ses données.

200 : ça a marché. 403 : accès refusé (clé absente ou refusée). 404 : introuvable. 429 : trop de demandes. 5xx : panne côté serveur ou intermédiaire.

Le petit serveur du kiosque ne fait que lire (GET). Le favori en POST reste un exemple, jamais exécuté.

À retenir. Une API renvoie des données, pas un écran : c’est l’application (ici Angular) qui compose les cartes. Le tri par pays n’est pas une nouvelle fonction de l’API : c’est un usage des données déjà reçues. Le même service pourrait donc alimenter une autre application, un portail ou un outil métier.

Conclusion de l’atelier

Les 5 messages à emporter

Phase 1 · découverte API

Sans clé l’API refuse (403), avec clé elle répond (200) : ce n’est pas de la magie, c’est un comportement normal et lisible.

Dans ce parcours : appels curl et lecture du JSON.

Phase 2 · IA appliquée

Copilot Covéa transforme l’appel curl en page web exploitable, à condition de relire le code généré.

Dans ce parcours : prompts HTML et test immédiat.

Phase 3 · standards web

DDD, API first, Richardson N2 et SPA accélèrent l’intégration quand front et BFF sont bien séparés.

Dans ce parcours : manipulations + lecture des appels.

Phase 4 · valeur métier

La même API alimente une autre application : le vote partagé du chat DSIN.

Dans ce parcours : ouverture de la modale, vote en un clic, classement commun.

Phase 5 · conclusion

On repart avec des repères concrets : contrat d’abord, standards web, séparation front/BFF, API réutilisable.

Dans ce parcours : synthèse finale et validation de la conclusion.

Et chez nous ? Un service peut « envelopper » une capacité existante : la modernisation peut se faire par étapes, sans tout réécrire d’un coup. Moderniser, ce n’est pas simplement repeindre le vieux chat : c’est rendre ses capacités utilisables sans devoir ouvrir toute la cuisine.
